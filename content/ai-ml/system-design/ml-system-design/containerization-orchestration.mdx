---
title: Containerization & Orchestration
description: How Docker and Kubernetes shape ML serving and training workloads, from GPU-aware scheduling to sidecars and serverless inference patterns.
---

Containers give ML teams a portable unit of deployment: the same image that passed integration tests in CI can run on a developer laptop, a GPU node in a private cluster, or a managed service in the cloud. For inference, that repeatability shortens incident response because you can bisect regressions by image digest rather than chasing host-level drift in CUDA drivers, Python packages, and system libraries. For training, images still help, but the dominant concerns shift to data locality, checkpoint durability, and job restart semantics when workers are preempted.

Kubernetes is the de facto orchestration layer for teams that need multi-tenant clusters, fine-grained placement, and declarative rollouts. GPU workloads add scheduling dimensions beyond CPU and memory: you must align device plugin reported capacity with node taints, tolerations, and often specialized operators that manage node pools, driver versions, and topology-aware placement for multi-GPU nodes. Community and vendor operators (for example NVIDIA GPU Operator patterns) automate driver and runtime lifecycle so cluster upgrades do not silently strand inference pods waiting for compatible runtimes. Knative, Cloud Run, and similar serverless abstractions trade some control for rapid scale-to-zero and request-based autoscaling, which suits bursty inference if cold start latency and maximum concurrency limits fit your SLO profile.

Resource requests and limits for GPUs are not interchangeable with CPU semantics. Under-scheduling leads to noisy neighbor contention on VRAM and PCIe bandwidth; over-reserving strands expensive silicon. Multi-container pods are useful when a primary model server benefits from a tightly coupled sidecar for observability export, authorization token minting, or gRPC/HTTP transcoding without extra network hops. Init containers are a natural place to pull large model weights from object storage, verify checksums, and warm filesystem caches before the main process binds its port, so the service does not advertise readiness until weights are local and integrity-checked. The recurring trade-off is coupling versus independence: sidecars simplify operations until their failure modes become entangled with the model container’s lifecycle, at which point separate Deployments with explicit service mesh policy may be clearer.

<InterviewQuestions>
  <InterviewQuestion question="When would you put model download logic in an init container instead of the main application container?" category="Infrastructure">
    Use an init container when you want strict ordering so the model process never starts listening until artifacts are present and verified, when you want different security contexts or credentials for pull-only storage access, or when you want to reuse a minimal, stable base image for the runtime while isolating heavy download tooling. The main container then focuses on serving logic and can restart without re-downloading if you mount a shared volume populated by the init step.
  </InterviewQuestion>
  <InterviewQuestion question="How do Kubernetes resource requests interact with GPU scheduling in practice?" category="Architecture">
    CPU and memory requests influence the scheduler’s fit, but GPUs are typically exposed as extended resources such as nvidia.com/gpu, and you must request integer or fractional units according to your device plugin and partitioning scheme. The scheduler also needs awareness of topology, shared multi-instance GPU slices if enabled, and taints that reserve nodes for training versus inference. Misconfigured requests can schedule a pod onto a node that reports GPUs while still failing at runtime if driver versions, CUDA capabilities, or MIG profiles do not match what the image expects.
  </InterviewQuestion>
  <InterviewQuestion question="What operational risks appear when mixing Knative-style scale-to-zero with low-latency inference SLOs?" category="Operations">
    Cold starts include image pull, runtime initialization, model load from disk or remote storage, and JIT compilation for some frameworks, any of which can breach tail latency budgets. Concurrency limits and surge handling during flash traffic can queue requests unless you keep minimum instances or predictive warm pools. You also need clear metrics on startup phases, budgets for always-warm canary pools, and fallback routing to a steady-state deployment when serverless capacity is throttled.
  </InterviewQuestion>
</InterviewQuestions>
